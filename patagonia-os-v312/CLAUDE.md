# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Patagonia OS — an ERP for "Carnes Patagonia" (a meat retailer), built as a real **multi-tenant** product so it can be sold to other butcher shops too: multiple companies now share the same Supabase project/database, isolated by `company_id` + RLS (not one Supabase project per client — that's a legacy/fallback path, see `docs/INSTALACION_NUEVO_CLIENTE.md`). npm workspaces monorepo, currently at v3.1.2. Documentation and code comments are written in Spanish; match that when editing docs, SQL comments, or user-facing strings.

## Commands

Run from the repo root (npm workspaces, Node >= 20):

```bash
npm install
npm run dev         # runs @patagonia/web (vite) only
npm run build        # builds domain -> web -> api, in that order
npm run test          # runs @patagonia/domain tests only (node --test)
npm run typecheck    # typechecks web and api
npm run lint          # lints web only
```

To work on a single workspace, use `-w`, e.g. `npm run dev -w @patagonia/api` (runs `tsx src/server.ts`, default port 8787). `@patagonia/domain` has no dev/lint script; its `build` (`tsc -p tsconfig.json`) must run before its `test` script, since tests run against compiled output in `dist/`, not source.

There is no root-level test runner beyond the domain package; `apps/web` and `apps/api` have no unit test scripts defined. `npm run lint -w @patagonia/web` currently fails in this checkout (`eslint.config.js` missing — pre-existing, unrelated to feature work). `npm run test:e2e` (root script) runs `tests/e2e/smoke.mjs` — read-only Playwright smoke checks (login, permission gating, platform-admin landing) against a **real** site + Supabase account, not mocks; needs `.env.test` (gitignored, see `.env.test.example`) with real credentials, and skips with a clear message if that file is missing.

## Architecture

Three workspaces plus a Supabase backend:

- `apps/web` (`@patagonia/web`): React + TypeScript + Vite frontend. This is the primary UI and the only workspace with a `dev` script wired into the root `npm run dev`.
- `apps/api` (`@patagonia/api`): Express + TypeScript API, intended for logic too sensitive for the client. Currently minimal — `apps/api/src/modules/sales/router.ts` only validates payloads with zod and returns `501`. All real business logic runs as Supabase RPCs/Edge Functions called directly from the frontend (see below); this API is not currently deployed by the Netlify config.
- `packages/domain` (`@patagonia/domain`): framework-free shared types and pure business logic (`Product`, `CartItem`, cart totals, profit/margin calculations, carcass cut-line totals, `assertSellable` stock guard). Both `web` and `api` depend on it. Compile it (`npm run build -w @patagonia/domain`) before consumers can pick up changes, since they import from `dist/`, not `src/`.
- `supabase/migrations`: numbered SQL migrations **001 through 027**, must be run **in order** against a Supabase Postgres project. `supabase/seed` has the "Carnes Patagonia" bootstrap data (`demo.sql`, `create_owner_profile.sql`), a generic `new_client_bootstrap.sql` template (legacy per-client-project path), and `create_platform_admin.sql` (bootstraps the one/few humans allowed to create new client companies in the shared project — see "Multi-tenant" below). `supabase/functions/create-staff-user` and `supabase/functions/create-client` are Deno Edge Functions (deployed separately via the Supabase Dashboard/CLI, not part of the npm build) — see "User provisioning" below for why they can't be plain SQL RPCs. Full step-by-step for onboarding a new client is `docs/INSTALACION_NUEVO_CLIENTE.md` (Camino A: shared DB, the default; Camino B: isolated Supabase project, legacy fallback). For rolling out a newer version of this repo to a client/project that's already live with real data, use `docs/ACTUALIZAR_CLIENTE_EXISTENTE.md` instead — it only runs the migrations after whatever that project's Supabase already has, since there's no migration-tracking table and blindly re-running from `001` (or a one-off data script like `011_reset_test_data.sql`) against a live database would be destructive.

### Core domain model (multi-company, multi-branch)

Every table hangs off `company_id` (and most off `branch_id`): `companies` → `branches` → `profiles` (linked 1:1 to `auth.users`, carries `role`) → `products`, `inventory_movements`, `shift_registers`/`shift_sales`/`shift_outflows`, `treasury_accounts`/`treasury_movements`, `suppliers`/`purchases`, `employees`/`payroll_liquidations`, `creditors`, `carcass_batches`, `audit_log`.

Key invariants (see `docs/ARCHITECTURE.md`, though it predates several modules below and should not be trusted over the code):
- Stock is never stored/edited directly — it is always the sum of `inventory_movements` rows (`products_with_stock` view). It increases via Compras (purchases), decreases via item-level sales in **Mostrador** (`features/sale/Sale.tsx`, `create_pos_sale` RPC, `027_pos_sales.sql`), and can be corrected from a physical count via the manual counter-adjustment RPC `adjust_product_stock` (`023_adjust_product_stock.sql`). Any of these quantity inputs must stay a plain `type="number"` field parsed with `Number()`, never the Argentine-money parser (`parseAmount()` in `lib/money.ts`) — mixing the two up was a real bug caught and fixed twice in this codebase.
- Two independent, intentionally-unlinked sales paths coexist: **Turnos** (`features/shifts/Shifts.tsx`) is one total per payment method per (branch, date, morning/afternoon) shift via `save_shift_sale` — feeds Tesorería, doesn't touch stock. **Mostrador** (`features/sale/Sale.tsx`) is item-by-item, deducts stock via `pos_sales`/`pos_sale_items` + `inventory_movements`, and does *not* write to `cash_movements`/`treasury_movements` — it's a deliberate design choice (confirmed with the user) to keep it separate from the Turnos/Tesorería total-based flow rather than reconcile the two. Turnos is gated by `sales.create` (owner/admin/manager/cashier); Mostrador has its own separate permission, `pos.sell`, currently granted only to owner/admin (`"*"`) — the business wanted to keep it owner-only for now rather than roll it out to staff immediately, unlike Turnos which every selling role already had. A role reaching Mostrador only sees `price_retail` and stock, never `cost`/margin (UI-level omission, not RLS — see the money-info bullet below).
- `create_sale_transaction`/`sales`/`sale_items` (`003_auth_and_sale_transaction.sql`) still exist in the schema but have no frontend caller and are effectively dead code — they're the old itemized-cart path tied to `cash_sessions` (open/close caja), which no longer has a frontend flow either. Don't extend them; `pos_sales`/`pos_sale_items` (above) is the live equivalent, built specifically to avoid the `cash_session_id not null` dependency.
- **Tesorería** (`treasury_accounts`/`treasury_movements`, `008_treasury_and_shifts.sql`) is the general ledger: every module that moves money (shift sales/outflows, supplier payments from Compras, manual adjustments/transfers) writes here, and `treasury_balance` (initial balance + ins − outs) is the source of truth for account balances.
- Row Level Security is enabled on every business table (`002_security.sql`, extended in `004_security_complete.sql`). Isolation is enforced via a `current_company_id()` SQL function that reads the caller's `profiles` row, used in `using (company_id = current_company_id())` policies. Never assume the client can be trusted to filter by company/branch — RLS is the actual boundary.
- **Multi-tenant / platform admins** (`025_platform_admins.sql`): the whole schema was already company-scoped, so real multi-tenancy just needed a way to create a new `companies` row without SQL. `platform_admins` is a separate table (no relation to `profiles`/`company_id` at all — a platform admin belongs to no company) checked by `am_i_platform_admin()`; a user in it lands on `features/admin/AdminCreateClient.tsx` instead of the normal company app (`App.tsx` checks `isPlatformAdmin && !profile` before the `Login`/`Layout` paths). The actual company+branch+owner creation runs in the Edge Function `create-client`, not a SQL RPC, for the same service-role reason as `create-staff-user`. A regular company `owner` must never be able to reach this — don't reuse `rolePermissions`/`"*"` for it.
- Every sensitive RPC follows the same skeleton: resolve caller via `auth.uid()` → look up their `profiles` row (company/role/active) → validate the target row(s) belong to that company/branch → row locks where money/stock is involved → insert/update → write `audit_log` → `revoke all ... from public` + `grant execute ... to authenticated`. Follow this exactly for new RPCs rather than inventing a new shape.
- **User provisioning** (`features/users`, `features/admin`): creating a new login (`auth.users` row) requires the Supabase Admin API, which needs the service-role key — that can never run as a plain `security definer` SQL function reachable by the anon key, so it's a separate Edge Function each for staff (`create-staff-user`, called by a company owner/admin) and for whole new clients (`create-client`, called by a platform admin only). Editing an existing user's role/branch/active flag *is* a normal RPC (`update_staff_user`, `024_update_staff_user.sql`) since it only touches `profiles`, not `auth.users`.
- Secrets: `VITE_*`-prefixed env vars are shipped to the browser; `SUPABASE_SERVICE_ROLE_KEY` must never be given a `VITE_` prefix or referenced from `apps/web`. The Edge Function reads it from its own auto-populated environment, never from a value passed in by the client.

### Frontend structure (`apps/web/src`)

- `lib/supabase.ts` exports a nullable `supabase` client and `isSupabaseConfigured` — several feature hooks check this flag to fall back to local "demo mode" (see `lib/demo-data.ts`) when Supabase env vars are absent. `App.tsx` uses this flag to decide whether to require login at all.
- `features/auth`: `AuthProvider.tsx` owns session/profile state — `loadProfile()` fetches the `profiles` row (with an embedded `companies(active)`) after login, signs the user out if the profile/company is missing/inactive, and falls back to checking `am_i_platform_admin()` when there's no profile row at all (see `isPlatformAdmin` below). `signIn()` calls `loadProfile()` directly *and* guards it with a `signingInRef` flag so the `onAuthStateChange` listener's own `SIGNED_IN` handling skips a redundant concurrent call — without that guard this was a real race in production (same query, same filter, one of the two concurrent calls came back empty, kicking the user back to the login screen). `permissions.ts` defines the `Permission` union, a `role -> Permission[]` map (`rolePermissions`). `owner` and `admin` are **not** equivalent despite both being full-access-ish roles: `owner` is `"*"` (everything, including internal-only tools still being trialed — `pos.sell`/`users.manage`/`audit.view` — reserved for the Patagonia OS team's own account, not sold to clients), while `admin` is an explicit list matching the commercial feature set a real client gets (sales, stock, purchases, treasury, employees, profitability, carcass, creditors, reports, branches — no Mostrador/Usuarios/Auditoría). Adding a new internal-only page: gate it behind a permission `owner` has via `"*"` but `admin`'s explicit list omits, the same way `pos.sell`/`users.manage`/`audit.view` are held back today. The `can(profile, permission)` check, and `PAGE_PERMISSIONS` (page → required permission — the single source of truth for the `Page` type and for `canAccessPage()`, which both `Layout.tsx` (nav filtering) and `App.tsx` (route guard) consume).
- `features/branches`: `BranchProvider.tsx`/`useActiveBranch()` — company-wide branch switcher context. Roles with `branches.manage` (owner/admin) see and can switch between *all* branches in the company and can create new ones (`+ Nueva sucursal`, `create_branch` RPC); other roles are pinned to their own `profile.branch_id`. Every other feature hook reads the active branch from here, not from `profile.branch_id` directly, so it scales automatically as branches are added.
- `features/users`: owner/admin-only screen to create logins for staff (email/name/role/branch → Edge Function `create-staff-user`, returns a one-time temp password shown in the UI) and to edit an existing user's role/branch/active flag (`update_staff_user` RPC). Distinct from `features/employees`, which is payroll (base salary, vales, liquidaciones), not login accounts.
- `features/admin`: platform-admin-only screen (`AdminCreateClient.tsx`) to create a brand-new client company + first branch + owner login in one step (Edge Function `create-client`), plus a list of existing companies with activate/deactivate (`list_companies_for_admin`/`set_company_active` RPCs, `026_admin_companies.sql`) — a deactivated company's users are blocked at login (`AuthProvider.loadProfile` checks the embedded `companies(active)`, not just `profiles.active`). Not reachable by any company role, including `owner` — gated entirely by `AuthProvider`'s `isPlatformAdmin`, not by `permissions.ts`.
- `features/audit`: owner/admin-only read of `audit_log` (date range + user filters, Spanish action labels with a raw fallback, expandable JSON detail) — no new RPC, it just queries the table directly since `audit_company_read` RLS (`004_security_complete.sql`) already scopes it correctly.
- `features/sale`: the Mostrador item-by-item sale screen — see the stock/sales bullets above.
- `features/shifts`, `features/inventory`, `features/purchases`, `features/employees`, `features/profitability`, `features/carcass`, `features/creditors`, `features/dashboard`: one feature folder per nav item in `Layout.tsx`. Several (Compras, Empleados, Despiece, Deudas) share the same print-to-paper/PDF pattern: a `.print-area`/`.no-print`/`.print-only-header` class scheme plus `window.print()`, driven by print-only global CSS.
- Feature-local `*-service.ts` files are the intended integration points with Supabase (RPC calls / table reads); keep Supabase-specific query/RPC code there rather than inside components. A matching `use*.ts` hook usually wraps the service with demo-mode fallback + local state.
- **Money vs. quantity inputs**: money fields use `type="text" inputMode="decimal"` parsed with `parseAmount()` (`lib/money.ts`, handles Argentine "." thousands / "," decimal separators); quantity/weight fields use `type="number" step="0.001"` parsed with plain `Number()`. Mixing these two up is a recurring real bug in this codebase (hit at least twice) — double-check which one applies before wiring a new numeric input.

## Deployment

This "Carnes Patagonia" instance: Netlify, manual drag-and-drop of `apps/web/dist` after `npm run build` (this project's Netlify site is **not** connected to the GitHub repo, so pushing to `main` does not deploy it — the dist folder has to be built and dragged in by hand each time). `netlify.toml` still declares the normal git-based build (`npm run build` → publish `apps/web/dist`, `/api/*` → Netlify functions) for when/if it's reconnected. Requires `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` set in Netlify env.

For a **new client**, connecting Netlify to their own GitHub repo (auto-deploy on push) is the recommended default instead of manual drag-and-drop — see `docs/INSTALACION_NUEVO_CLIENTE.md`.
