# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Patagonia OS — an ERP for "Carnes Patagonia" (a meat retailer), built as a real **multi-tenant** product so it can be sold to other butcher shops too: multiple companies now share the same Supabase project/database, isolated by `company_id` + RLS (not one Supabase project per client — that's a legacy/fallback path, see `docs/INSTALACION_NUEVO_CLIENTE.md`). npm workspaces monorepo, currently at v3.1.2. Documentation and code comments are written in Spanish; match that when editing docs, SQL comments, or user-facing strings.

## Commands

Run from the repo root (npm workspaces, Node >= 20):

```bash
npm install
npm run dev         # runs @patagonia/web (vite) only
npm run build        # builds domain -> web -> api, in that order
npm run test          # builds and tests @patagonia/domain (node --test), then runs the @patagonia/web unit tests (tsx + node --test, src/**/*.test.ts)
npm run typecheck    # typechecks web and api
npm run lint          # lints web only
```

To work on a single workspace, use `-w`, e.g. `npm run dev -w @patagonia/api` (runs `tsx src/server.ts`, default port 8787). `@patagonia/domain` has no dev/lint script; its `build` (`tsc -p tsconfig.json`) must run before its `test` script, since tests run against compiled output in `dist/`, not source.

`apps/web` has unit tests for its pure logic (scale barcode parsing incl. the Kretz Aura "ticket de total", `parseAmount`, CSV escaping, Argentina date helpers) — keep pure logic free of `lib/supabase` imports so it stays testable (that's why `scale-barcode.ts` was split out of `scale-config-service.ts`); test files are excluded from `tsc`. `apps/api` has no unit test scripts. `npm run lint -w @patagonia/web` currently fails in this checkout (`eslint.config.js` missing — pre-existing, unrelated to feature work). `npm run test:e2e` (root script) runs `tests/e2e/smoke.mjs` — read-only Playwright smoke checks (login, permission gating, platform-admin landing) against a **real** site + Supabase account, not mocks; needs `.env.test` (gitignored, see `.env.test.example`) with real credentials, and skips with a clear message if that file is missing.

## Architecture

Three workspaces plus a Supabase backend:

- `apps/web` (`@patagonia/web`): React + TypeScript + Vite frontend. This is the primary UI and the only workspace with a `dev` script wired into the root `npm run dev`.
- `apps/api` (`@patagonia/api`): Express + TypeScript API, intended for logic too sensitive for the client. Currently minimal — `apps/api/src/modules/sales/router.ts` only validates payloads with zod and returns `501`. All real business logic runs as Supabase RPCs/Edge Functions called directly from the frontend (see below); this API is not currently deployed by the Netlify config.
- `packages/domain` (`@patagonia/domain`): framework-free shared types and pure business logic (`Product`, `CartItem`, cart totals, profit/margin calculations, carcass cut-line totals, `recipeCost` recipe costing, `assertSellable` stock guard). Both `web` and `api` depend on it. Compile it (`npm run build -w @patagonia/domain`) before consumers can pick up changes, since they import from `dist/`, not `src/`.
- `supabase/migrations`: numbered SQL migrations (**001 through 094** as of 2026-09-24 — check the actual directory listing rather than trusting this number, it goes stale), must be run **in order** against a Supabase Postgres project. `supabase/seed` has the "Carnes Patagonia" bootstrap data (`demo.sql`, `create_owner_profile.sql`), a generic `new_client_bootstrap.sql` template (legacy per-client-project path), and `create_platform_admin.sql` (bootstraps the one/few humans allowed to create new client companies in the shared project — see "Multi-tenant" below). `supabase/functions/create-staff-user` and `supabase/functions/create-client` are Deno Edge Functions (deployed separately via the Supabase Dashboard/CLI, not part of the npm build) — see "User provisioning" below for why they can't be plain SQL RPCs. Full step-by-step for onboarding a new client is `docs/INSTALACION_NUEVO_CLIENTE.md` (Camino A: shared DB, the default; Camino B: isolated Supabase project, legacy fallback). For rolling out a newer version of this repo to a client/project that's already live with real data, use `docs/ACTUALIZAR_CLIENTE_EXISTENTE.md` instead — blindly re-running from `001` (or a one-off data script like `011_reset_test_data.sql`) against a live database would be destructive. **Migration registry, from `099` on** (`099_schema_migrations_registry.sql`): every migration file's last line does `insert into public.schema_migrations (version) values ('NNN_name') on conflict do nothing;` — that table has RLS with no policies at all (not even a read one), so it's only touched by whoever applies migrations, never by the app. `select version from public.schema_migrations order by version;` on a project shows what it actually has; compare prod vs. staging before assuming they're in sync — they silently drifted once already (staging was missing `091` for days, only surfaced when `098`'s `get_branches_overview` broke on it). `001`–`098` are NOT backfilled into the table (no reliable way to know from outside which of those any given project actually has), so the registry only covers `099`+. A Supabase MCP connector (`.mcp.json`, token in the owner's Windows env vars) gives Claude direct `execute_sql`/`apply_migration`/`get_advisors` access to both the production project (`tayylvhfmoybchutybcz`) and a staging project (`loquhcwsvsbqpinefxcc`, "patagonia-os-pruebas") — prefer it over asking the user to paste SQL into the dashboard, and pass `project_id` explicitly every time since there are two.

### Core domain model (multi-company, multi-branch)

Every table hangs off `company_id` (and most off `branch_id`): `companies` → `branches` → `profiles` (linked 1:1 to `auth.users`, carries `role`) → `products`, `inventory_movements`, `shift_registers`/`shift_sales`/`shift_outflows`, `treasury_accounts`/`treasury_movements`, `suppliers`/`purchases`, `employees`/`payroll_liquidations`, `creditors`, `carcass_batches`, `audit_log`.

Key invariants (see `docs/ARCHITECTURE.md`, though it predates several modules below and should not be trusted over the code):
- Stock is never stored/edited directly — it is always the sum of `inventory_movements` rows (`products_with_stock` view). It increases via Compras (purchases), decreases via item-level sales in **Mostrador** (`features/sale/Sale.tsx`, `create_pos_sale` RPC, `027_pos_sales.sql`), and can be corrected from a physical count via the manual counter-adjustment RPC `adjust_product_stock` (`023_adjust_product_stock.sql`). Any of these quantity inputs must stay a plain `type="number"` field parsed with `Number()`, never the Argentine-money parser (`parseAmount()` in `lib/money.ts`) — mixing the two up was a real bug caught and fixed twice in this codebase.
- **Presentaciones / stock compartido (migration `111_shared_stock_products.sql`, LIVE 2026-10-08, all plans).** One piece of merchandise sold at several prices (oferta 3 kg, mayorista, cajón x15) is several products with their own code/price/PLU. `products.stock_source_id` points a "presentación" at its principal, and `stock_factor` is how much of the principal each unit takes (1 if same unit, 15 for a cajón x15 of a kg product). The BEFORE INSERT trigger `inventory_movements_use_stock_source` rewrites EVERY movement of a presentación to the principal (quantity × factor, original kept in `via_product_id`). So no stock-moving RPC had to change, and new ones get it for free. Do not bypass it by computing stock per variant. `movement_type='adjustment'` on a presentación is rejected (adjust the principal). `products_with_stock.stock` for a presentación = principal ÷ factor. Link/unlink only via `set_product_stock_source` (zeroes the variant's own balance, optionally moves it to the principal). `products_stock_source_guard` forbids chains. UI: Stock → "Presentaciones" on the principal, or Editar → bloque "Stock"; Sucursales hides presentaciones from transfers.
- Two sales paths coexist and **both feed Tesorería, with no reconciliation between them** — this is a real open risk, not a resolved design: **Turnos** (`features/shifts/Shifts.tsx`; **hidden from the menu since 2026-09-24** — only Carnes Patagonia ever used it and it stopped on 2026-09-15; the screen, tables and history are kept, re-enable by adding the `shifts` entry back to `navGroups` in `Layout.tsx`, which also closes the double-counting risk described below; since 2026-10-03 the per-branch "Modo de venta" selector, its Sucursales column and the Mostrador "this branch sells by Turnos" confirm are also removed from the UI — `branches.sales_mode` and `set_branch_sales_mode` stay in the DB) is one total per payment method per (branch, date, morning/afternoon) shift via `save_shift_sale`, entered by hand at shift close. **Mostrador** (`features/sale/Sale.tsx`) is item-by-item, deducts stock via `pos_sales`/`pos_sale_items` + `inventory_movements`, and — as of `036_pos_sale_treasury.sql` — the checkout screen requires picking a `treasury_accounts` row and `create_pos_sale` writes a `'venta'` `treasury_movements` row per sale, same `movement_type` Turnos uses. Originally Mostrador deliberately did *not* touch Tesorería at all, specifically to avoid double-counting against the Turnos manual total; that gap was closed once Carnes Patagonia started using Mostrador for real, but **nothing stops a cashier from also including a Mostrador sale in that day's manually-typed Turnos total**, double-counting it in Tesorería. There is no automated reconciliation between the two paths — if you touch either, keep this in mind and flag it to the user rather than assuming it's handled. Turnos is gated by `sales.create` (owner/admin/manager/cashier); Mostrador has its own permission, `pos.sell`, granted to owner (`"*"`) and admin. A role reaching Mostrador only sees `price_retail` and stock, never `cost`/margin (UI-level omission, not RLS — see the money-info bullet below).
- `create_sale_transaction`/`sales`/`sale_items` (`003_auth_and_sale_transaction.sql`) still exist in the schema but have no frontend caller and are effectively dead code — they're the old itemized-cart path tied to `cash_sessions` (open/close caja), which no longer has a frontend flow either. Don't extend them; `pos_sales`/`pos_sale_items` (above) is the live equivalent, built specifically to avoid the `cash_session_id not null` dependency.
- **Tesorería** (`treasury_accounts`/`treasury_movements`, `008_treasury_and_shifts.sql`) is the general ledger: every module that moves money (shift sales/outflows, supplier payments from Compras, manual adjustments/transfers) writes here, and `treasury_balance` (initial balance + ins − outs) is the source of truth for account balances.
- Row Level Security is enabled on every business table (`002_security.sql`, extended in `004_security_complete.sql`). Isolation is enforced via a `current_company_id()` SQL function that reads the caller's `profiles` row, used in `using (company_id = current_company_id())` policies. Never assume the client can be trusted to filter by company/branch — RLS is the actual boundary.
- **A `create or replace view` runs as its owner (`postgres`), bypassing RLS on its underlying tables** — this has caused two real cross-company data leaks so far (`031_fix_view_rls_bypass.sql`, then `customer_balance` again in `050_fix_customer_balance_rls_bypass.sql`). Any view granted `select` to `authenticated` (`treasury_balance`, `products_with_stock`, `supplier_balance`, `creditor_balance`, `customer_balance`, `products_price_list`, ...) **must** filter by `company_id = current_company_id()` (or an equivalent join) *inside the view itself* — RLS on the underlying tables does not protect it. When adding a new such view, copy this pattern and re-run Supabase's security advisor (`get_advisors`, via the MCP connector below) afterward.
- **Internal `security definer` helpers that take ids and do NOT check the caller's company must be revoked from `anon, authenticated` explicitly**, not just `from public`: `authenticated` still gets EXECUTE through the default privileges (caught by `get_advisors` on 2026-09-30, `scale_control_totals`/`scale_control_window`, fixed within minutes, before the web shipped). Run `get_advisors` after every migration and look for new names under `authenticated_security_definer_function_executable`.
- Function `EXECUTE` also defaults open in Postgres: a bare `grant execute ... to authenticated` does **not** revoke the implicit grant to the `PUBLIC` pseudo-role (which every role, including unauthenticated `anon`, inherits). `052_revoke_public_execute_on_functions.sql` closed this project-wide; keep following the RPC skeleton below for new functions, and it's already covered by `alter default privileges`.
- **Multi-tenant / platform admins** (`025_platform_admins.sql`): the whole schema was already company-scoped, so real multi-tenancy just needed a way to create a new `companies` row without SQL. `platform_admins` is a separate table (no relation to `profiles`/`company_id` at all — a platform admin belongs to no company) checked by `am_i_platform_admin()`; a user in it lands on `features/admin/AdminCreateClient.tsx` instead of the normal company app (`App.tsx` checks `isPlatformAdmin && !profile` before the `Login`/`Layout` paths). The actual company+branch+owner creation runs in the Edge Function `create-client`, not a SQL RPC, for the same service-role reason as `create-staff-user`. A regular company `owner` must never be able to reach this — don't reuse `rolePermissions`/`"*"` for it.
- Every sensitive RPC follows the same skeleton: resolve caller via `auth.uid()` → look up their `profiles` row (company/role/active) → validate the target row(s) belong to that company/branch → row locks where money/stock is involved → insert/update → write `audit_log` → `revoke all ... from public` + `grant execute ... to authenticated`. Follow this exactly for new RPCs rather than inventing a new shape.
- **User provisioning** (`features/users`, `features/admin`): creating a new login (`auth.users` row) requires the Supabase Admin API, which needs the service-role key — that can never run as a plain `security definer` SQL function reachable by the anon key, so it's a separate Edge Function each for staff (`create-staff-user`, called by a company owner/admin) and for whole new clients (`create-client`, called by a platform admin only). Editing an existing user's role/branch/active flag *is* a normal RPC (`update_staff_user`, `024_update_staff_user.sql`) since it only touches `profiles`, not `auth.users`.
- Secrets: `VITE_*`-prefixed env vars are shipped to the browser; `SUPABASE_SERVICE_ROLE_KEY` must never be given a `VITE_` prefix or referenced from `apps/web`. The Edge Function reads it from its own auto-populated environment, never from a value passed in by the client.
- **Bank reconciliation (`features/reconciliation`, migration `103_bank_reconciliation.sql`, page "Conciliación" under Finanzas, `treasury.manage` + plan **Full** (owner rule 2026-09-29: new screens start in Full; they can later move down a plan, never up); LIVE 2026-09-30)**: Redesigned after a REAL statement: Banco Provincia, Sept 2026, 1,227 lines, a genuine binary `.xls` from JasperReports. It must work for ANY bank, so there is no per-bank reader. `bank-statement.ts` (pure, tested) finds the header row under any bank preamble, guesses columns by synonyms, parses AR/US amounts and dmy/mdy/ymd/"30-sept-2026" dates, and skips balance/total/disclaimer rows. The person confirms or fixes the mapping and it is saved on the account. `read-statement-file.ts` reads .xlsx, binary .xls (SheetJS 0.20.3 from cdn.sheetjs.com, lazy-loaded), HTML-table ".xls" and CSV; PDF is rejected. What the real data showed, and so the model: (1) one bank account receives money from SEVERAL Tesorería accounts, hence `bank_reconciliation_accounts` = name + `treasury_account_ids` + `card_account_ids` (posnet) + `main_treasury_account_id` (where fees and taxes are booked). (2) Mostrador books ONE `venta` per account per shift close (`reference_type='pos_shift'`), so the system side (`get_reconciliation_items`) uses the individual `pos_sale_payments` instead and excludes those totals. Turnos-era `venta` (`reference_type='shift'`) and every other movement are included. (3) `reconcile-match.ts`: 1:1 exact amount, −3..+7 days. It matched 258/321 real transfers. (4) Cards are deposited per batch/brand/business day net of fees ("PAGOS A COMERCIOS VISA - L. …"), so they are NOT matched per sale: `summarizeCards` compares sold vs credited per period (real: 4.8%), and `mark_bank_lines_card_deposit` reconciles the deposits. (5) Repeated bank-only lines (e.g. 89× "IMPUESTO CREDITO -LEY 25413") are grouped (`groupSimilarLines`) and booked in one call (`create_movements_from_bank_lines`). `bank_line_matches` holds exactly one of `movement_id`/`payment_id`, each matched once. Batch confirm: `confirm_bank_matches` (all or nothing). **Tolerance + channel report (migration 105, 2026-09-30, the owner asked for it "como las grandes empresas")**: the matcher has a second pass of "near" matches: same sign, same date window, |diff| ≤ max($500, 2%) (`nearTolerance`, the same cap enforced in SQL), smallest diff first. `confirm_bank_match` takes `p_adjustment` (default 0, so older callers still work). The diff is booked as an `ajuste` "Diferencia de cobro (conciliación)" on the main account and removed on undo. On the real data: 258 exact + 58 near = 316 of the 321 transfer charges. `summarizeByChannel`/`bankChannel` build the "banco vs sistema" inflow table per channel (transferencias/tarjetas/billeteras/otros) at the top of the screen. Movements the reconciliation itself created are excluded from the system side. Every RPC has `require_plan('full')` and owner/admin only. Staging lacks `pos_sale_payments.reference` (it drifted), so this was tested on prod inside rollback-only transactions. **Third round (migration 106, 2026-09-30, owner said "hacé todo")**:
  - **Undelivered-transfer alert.** `get_reconciliation_alerts(recon_id|null)`: non-card Mostrador cobros at least 3 days old, inside the date range the imported statements cover, unmatched, and with no similar bank line (±max($500, 2%), −3..+7 days). Includes the cashier's name. Shown in `TransferAlerts.tsx` and in Inicio's "Alertas" (the fake transfer-receipt scam).
  - **Rules.** `bank_reconciliation_rules` = uppercase `match_text` + direction + action (expense+category, income, customer, ignore). `findRule`/`suggestRuleText` in `reconcile-match.ts` propose the payer's CUIT, or the literal leading text. `apply_reconciliation_rules([{line_id, rule_id}])` re-checks text and direction in SQL. UI is `RuleForm.tsx` ("¿Qué es? / Regla").
  - **Customer payment from a bank line.** `create_customer_payment_from_bank_line` calls `register_customer_payment`, so the customer's debt goes down. The owner's real September DEBIN credits ($900k, 34 different CUITs) are customers paying from wallets, NOT Mercado Pago transfers. `undo_bank_match` was rewritten to delete that `customer_payments` row first (its FK to `treasury_movements` is NO ACTION).
  - **Period close.** `bank_reconciliation_closes`, plus the trigger `bank_lines_closed_period_guard`. It blocks changing matched/ignored lines dated ≤ a close; pending lines can still be matched; new lines inside a closed period are silently skipped on import and counted as "repeated". `reconciliation_system_balance` = the group's treasury balance at a date. `ClosePeriod.tsx` shows the classic sheet from `buildClosingSheet`: bank − bank-only + system-only + cards gap vs system, printed via a portal `.print-area`. `closingBalanceFromLines` picks the day's final balance without knowing the bank's row order.
  - **Card cost.** `cardCostByMonth` and `depositsByBrand`.
  - **Mercado Pago.** Report headers (`NET_CREDIT_AMOUNT`/`NET_DEBIT_AMOUNT`/`BALANCE_AMOUNT`/`SETTLEMENT_NET_AMOUNT`) were added to the synonyms. NOT yet tested with a real MP file.
  - **Alert settings (migration 107)**: per bank account `alerts_enabled` / `alert_days` (1-30, default 3) / `reminder_days` (0-90, default 7, 0 = off), set via `set_reconciliation_alert_settings` from the account form ("Avisos"). The alert can only compare against uploaded statements, so `get_reconciliation_reminders()` lists accounts whose last statement line is older than `reminder_days`; shown in Inicio ("Subí el resumen de …") and at the top of Conciliación.
  - Tested on prod in rollback-only DO blocks, including the rules, the customer debt going down and coming back, the close lock and reopen, the import skip, and the alerts (35 ms over real September data). Staging has no profiles to impersonate.
- **Plans (Básico/Estándar/Full, migration `101_company_plans.sql`, 2026-09-29)**: `companies.plan` (`basico|estandar|full`; every company that existed before is `full`). What each plan includes and its limits: header of that migration + `permissions.ts` (`PLAN_LIMITS`, `PERMISSION_MIN_PLAN`, `PAGE_MIN_PLAN`, `planAllows`, `profilePlan`). `can()`/`canAccessPage()` already check the plan, so the nav, the route guard and any `can(profile, "customers.manage")` hide what the plan lacks. In the DB (owner decision: NO global PostgREST db-pre-request hook, so an error can never block every company at once):
  - Each gated RPC starts with `perform public.require_plan('estandar'|'full');`. The migration injected it into the live definition of each function in each DB. **When you rewrite one of those functions, keep that line as the first statement of the body.** List them with `select proname from pg_proc where prosrc like '%require_plan(%';`.
  - Their tables have a restrictive RLS policy `plan_estandar`: if the plan is too low they read as empty and can't be written.
  - Branch/user limits are triggers on `branches`/`profiles` (insert or reactivation). They never deactivate anything that already exists.
  - Not enforced in the DB, UI only: the cable scale (Web Serial), the per-person "Qué puede ver" checkboxes (inside `update_staff_user`), and the `customer_balance`/`creditor_balance` views.
  - Platform admin: `set_company_plan`/`list_company_plans`, plan selector on each card and in the new-client form.
  - `AuthProvider` falls back to the old select if `companies.plan` doesn't exist yet (42703), so the web can never lock people out ahead of the migration.
  - Staging had drifted a lot from prod on these functions (older signatures, two functions missing). That is why the injection works on each DB's own definitions instead of copying bodies.
- **Payroll (`features/employees`, `054_payroll_split_payments_and_periods.sql`)**: `employees.salary_period` is `daily | weekly | biweekly | monthly` (divisor 1/7/14/30 in `close_payroll_liquidation`); `payroll_liquidations.base_salary` stores the *prorated* amount for that period, not the nominal salary. A liquidación's net can be split across multiple `treasury_accounts` in one go — `close_payroll_liquidation(p_payments jsonb)` takes an array of `{account_id, amount}` (same shape as `create_pos_sale`'s items), validates the sum matches the net exactly, and writes one `treasury_movements` row + one `payroll_liquidation_payments` row per entry (mirrors `pos_sale_payments`). Both `shift_outflows` (vales) and `payroll_adjustments` (premios/descuentos) get stamped with `payroll_liquidation_id` when a liquidación consumes them, so a closed liquidación's exact line items can be reconstructed later for the printable recibo (`listPayrollLiquidationDetail` in `employees-service.ts`) instead of only showing the stored totals. `delete_payroll_liquidation` unlinks those vales/adjustments back to "pendiente" and must delete `payroll_liquidations` (which cascades `payroll_liquidation_payments`) **before** deleting the linked `treasury_movements` rows, not after — the FK from `payroll_liquidation_payments.treasury_movement_id` blocks deleting a movement that's still referenced (caught by a direct SQL test against staging before this reached production).

### Frontend structure (`apps/web/src`)

- `lib/supabase.ts` exports a nullable `supabase` client and `isSupabaseConfigured` — several feature hooks check this flag to fall back to local "demo mode" (see `lib/demo-data.ts`) when Supabase env vars are absent. `App.tsx` uses this flag to decide whether to require login at all.
- `features/auth`: `AuthProvider.tsx` owns session/profile state — `loadProfile()` fetches the `profiles` row (with an embedded `companies(active)`) after login, signs the user out if the profile/company is missing/inactive, and falls back to checking `am_i_platform_admin()` when there's no profile row at all (see `isPlatformAdmin` below). `signIn()` calls `loadProfile()` directly *and* guards it with a `signingInRef` flag so the `onAuthStateChange` listener's own `SIGNED_IN` handling skips a redundant concurrent call — without that guard this was a real race in production (same query, same filter, one of the two concurrent calls came back empty, kicking the user back to the login screen). `permissions.ts` defines the `Permission` union, a `role -> Permission[]` map (`rolePermissions`). `owner` and `admin` are **not** equivalent despite both being full-access-ish roles: `owner` is `"*"` (everything, including internal-only tools still being trialed — `users.manage`/`audit.view` — reserved for the Patagonia OS team's own account, not sold to clients), while `admin` is an explicit list matching the commercial feature set a real client gets (sales, stock, purchases, treasury, employees, profitability, carcass, creditors, reports, branches, Mostrador — no Usuarios/Auditoría). `pos.sell` (Mostrador) used to be held back from `admin` the same way — it moved to the `admin` list once Carnes Patagonia started using Mostrador for real in the shop, not just internally. Adding a new internal-only page: gate it behind a permission `owner` has via `"*"` but `admin`'s explicit list omits, the same way `users.manage`/`audit.view` are held back today. The `can(profile, permission)` check, and `PAGE_PERMISSIONS` (page → required permission — the single source of truth for the `Page` type and for `canAccessPage()`, which both `Layout.tsx` (nav filtering) and `App.tsx` (route guard) consume).
- `features/branches`: `BranchProvider.tsx`/`useActiveBranch()` — company-wide branch switcher context. Roles with `branches.manage` (owner/admin) see and can switch between *all* branches in the company and can create new ones (`+ Nueva sucursal`, `create_branch` RPC); other roles are pinned to their own `profile.branch_id`. Every other feature hook reads the active branch from here, not from `profile.branch_id` directly, so it scales automatically as branches are added. `Branches.tsx` (2026-09-29, migration `098_branches_overview.sql`, permission `branches.manage`, nav item "Sucursales" under "Equipo"): a resumen-per-branch screen (`get_branches_overview` RPC: stock at cost, today's sales, open-shift flag, plus a consolidated total across all branches) and a stock transfer between branches (`transfer_branch_stock` RPC — two `inventory_movements` rows, `transfer_out`/`transfer_in`, sharing one `reference_id`; locks the product row, not a `sum()`, since Postgres won't `FOR UPDATE` an aggregate; rejects if the source branch doesn't have enough). `treasury_accounts.branch_id` (same migration) is nullable — null (the default, unchanged for every existing account) means shared by all branches; set to one branch via `set_treasury_account_branch` (Tesorería's per-account dropdown, only shown once a company has 2+ branches) to keep that branch's posnet/bank separate. `listTreasuryAccounts(branchId?)` filters to shared + that branch's own accounts when a branchId is passed (Mostrador's `useTreasury`), and returns everything when it's omitted (Tesorería, owner/admin). Verified end-to-end against staging with the real `@supabase/supabase-js` client (not just raw SQL) as a signed-in user, including the RLS-filtered account list per branch and the overview numbers before/after a transfer.
- `features/users`: owner/admin-only screen to create logins for staff (email/name/role/branch → Edge Function `create-staff-user`, returns a one-time temp password shown in the UI) and to edit an existing user's role/branch/active flag (`update_staff_user` RPC). Distinct from `features/employees`, which is payroll (base salary, vales, liquidaciones), not login accounts.

## Thermal ticket printing (print agent, 2026-09-28)

Ticket printing must work for ANY thermal ESC/POS printer without per-brand drivers, so the recommended path is the local **print agent**: `apps/web/public/patagonia-print-agent.ps1` (PowerShell 5.1 HttpListener on `127.0.0.1:9101`, ASCII-only file, runs without admin; installed once per PC by `apps/web/public/instalar-impresora.bat`, which downloads it from the site and adds a Startup shortcut). `features/sale/printer-agent.ts` (client + `pickLikelyThermal`, tested), `PrinterAgentSettings.tsx` (block "Impresora de tickets" in the Mostrador gear panel: status, printer picker, test ticket) and `thermal-printer.ts` (`printBytes`: agent first, then WebUSB, `autoPrintReceipt` in `Sale.tsx` never falls back to the Windows dialog when the agent is active) tie it together. The agent receives the ESC/POS bytes already built by `TicketBuilder` and writes them to a Windows queue in RAW mode.

Why the other paths fail (real incident, Unnion UN-TP95W): Windows auto-installs an inbox **v4 class driver** ("Brother … Leg Type1 Class Driver") for many thermal printers. WebUSB then gets "Access denied", and the normal print dialog / `--kiosk-printing` renders through that laser driver, so the thermal printer prints the byte stream as text (meters of garbage). v4 queues also reject RAW jobs (MS_XPS_PROC fails, 0x8051100F), so the agent creates a companion queue `"<name> (ticket)"` using the v3 inbox driver **"Generic / Text Only"** on the same port; verified byte-for-byte pass-through, and `Add-PrinterDriver/Add-Printer/Set-Printer` all work without admin. Security: Origin allowlist (`*.patagoniasystem.com.ar`, localhost), Host check, POST needs Origin, only physical printers. Chrome ≥142 asks a "local network access" permission the first time a site talks to localhost, so the web app only probes the agent when a person clicks "buscar" or once it was found before (`isAgentEnabled`). Verified with real Chrome 153 (Playwright, permission granted) and a file-backed test queue; NOT yet with a real USB thermal printer. `kiosco-impresora.bat` (kiosk shortcut + `AddForm` of a "Rollo80mm" size, needs `\\COMPUTERNAME` not NULL as server name) remains only as a last resort for PCs whose Windows driver is already the correct one.

## Scale Manager (driver-based architecture, 2026-09-29)

`apps/web/src/features/scales/` is a driver/adapter architecture for scales, built on top of the Kretz-specific code below (nothing in `scale-weight.ts`/`scale-weight-parser.ts`/`scale-serial.ts` was rewritten — it's wrapped, not replaced). Goal: only a brand/model that's been physically validated gets called "compatible," and adding a new brand later never touches the core.

- `types.ts`: the `ScaleDriver` interface — `id`/`brand`/`models`, `status: "certified" | "experimental"`, `capabilities: ScaleCapability[]` (`readWeight`, `readPlu`, `writePlu`, `bulkSync`, `readCatalog`, `ping`), and optional methods (`identify`, `readWeight`, `ping`, `readPlu`, `writePlu`, `deletePlu`, `runCertificationTest`) — a driver implements only what it can actually do. **experimental never gets to silently hand back a wrong weight or price**: a driver's own methods stay honest about it (`ScaleWriteResult.verified: "confirmed" | "unconfirmed" | "failed"`), and the UI/sync layer never upgrades "unconfirmed" to a success message.
- `registry.ts`: `SCALE_DRIVERS` — the list of drivers. Adding a brand = one new file under `drivers/` + one line here; no other file changes.
- `drivers/kretz-aura-weight.ts` / `drivers/kretz-report-plu.ts`: thin wrappers around the existing, already-proven Kretz code (see the section below) — the Aura weight exchange (drain, send "W", collect/parse the frame, error texts) lives ONCE in `features/sale/scale-weight-protocol.ts` (`exchangeWeightFrame`/`weightReadError`), shared by Mostrador (`scale-weight.ts`) and the driver since 2026-09-29; only port opening differs. Behavior locked by fake-port tests (`kretz-aura-weight.test.ts`, `scale-weight*.test.ts`, helper `sale/test-fake-serial.ts`) — both `status: "certified"`, since both are the same hardware already confirmed in production. `kretz-report-plu`'s `writePlu` does an optional read-back price check (`settings.verifyWrite`, default true) before calling a write "confirmed" — see `sync.ts`.
- `manager.ts`: `detectScaleOnPort()` (tries each registered driver's `identify()` against a freshly-picked port, certified drivers first), `callResilient()` (generic close/reopen-once retry for new drivers to use — the two existing Kretz files keep their own already-proven retry logic, not migrated to this), `reconnectSavedConnections()` (re-runs each saved connection's own driver handshake against already-granted ports on load — Web Serial has no persistent device id, so this is a real recognition, not a guess), `onScalePortDisconnect()`, and the `ScaleConnectionRecord` list (`localStorage` key `patagonia-scale-connections`) that lets **more than one scale be configured on the same PC/branch** (e.g. a weight scale for Mostrador and a PLU scale for Stock at once).
- `diagnostics.ts` (`runScaleDiagnostics`): step-by-step plain-language check (connectivity → main capability) for the "Diagnosticar" button — distinct from the one-shot "Probar" done at setup.
- `sync.ts`: resumable, verified bulk sync. Each product's state is `pending | confirmed | uncertain | failed`, persisted per-connection (`patagonia-scale-sync-session-<id>`) after every single item — an interrupted sync knows exactly what's confirmed and only retries the rest, never resends blindly. Security over speed: verification is on by default whenever the driver can reasonably confirm a write.
- `activity-log.ts`: local rolling log of detect/test/certification/sync/error events (capped at 200 entries). It is only uploaded when the owner/admin clicks "Enviar a soporte" on the Balanzas screen (2026-09-29, migration `100_scale_support_reports.sql`). `submit_scale_support_report` stores the log, the saved connections (+ last diagnostic), the user agent and an optional note, with a cap of 20 per company per day. The table has RLS and no policies. Only platform admins read it, via `list_scale_support_reports` / `set_scale_support_report_resolved`, shown as "Reportes de balanzas" on `AdminCreateClient.tsx` (`AdminScaleReports.tsx`). No sales/prices/customer data are sent. "Copiar para soporte" is still there as a fallback.
- **HIDDEN FROM THE MENU since 2026-09-30** (owner: "¿por qué aparece Balanzas si se configura desde Productos, por qué hay 2 formas?"). It duplicated the paths clients already use daily (price upload through it was tested once with a real Kretz Report LT and went fine; Aura weight through it never). Clients use Productos/Stock → "Balanza por cable" (`ScaleSyncPanel`, which now also logs to `activity-log.ts` and has "Enviar a soporte" for owner/admin) and the Mostrador gear (`ScaleWeightSettings`) for Aura weight. The code, route and permission are intact: re-add the `scales` entry in `Layout.tsx` navGroups (and the Balanzas section in the help-chat GUIDE) if the owner decides it should be the single place instead.
- `Scales.tsx` (nav, currently hidden: "Producto y stock" → "Balanzas", permission `scales.manage` = owner via `"*"` and admin): the actual **Conectar → Detectar → Probar → Guardar** screen. No COM/baud/checksum/protocol ever shown outside the collapsed "Configuración avanzada". **Additive, not a replacement** — `ScaleWeightSettings.tsx` (Mostrador gear) and `ScaleSyncPanel.tsx` (Stock) still work exactly as before; nothing was removed. Only migrate/retire those once the new screen has proven itself in real use. **Weight scales are linked to Mostrador (2026-09-29)**: saving a connection whose `confirmedCapabilities` include `readWeight` (cashier said "Sí, coincide") sets the same `patagonia-weight-scale-enabled` flag the gear panel sets and hands the port to `scale-weight.ts` via `setWeightScalePort()` (re-done on every Balanzas `refresh()`, after reconnect); removing the last weight connection disables it. `scale-weight.ts` `getPort()` no longer blindly takes `getPorts()[0]` when 2+ ports are authorized: it asks each *closed* port for the weight and keeps the one that answers (ports already open elsewhere, e.g. a PLU sync, are skipped) — covered by `scale-weight.test.ts` with fake ports. `scale-serial.ts` (PLU) still takes `getPorts()[0]` — same limitation as below. **Unplug/replug (2026-09-29)**: in real use the PLU scale is plugged in only to send prices and then unplugged. `scale-serial.ts` and `scale-weight.ts` listen to Web Serial `disconnect` and drop their cached port when it is theirs, and the Balanzas screen releases dead ports from the Manager (`releaseDisconnectedPort`) and re-runs `reconnectSavedConnections()` on `connect`, so replugging works without reloading the page (`*-replug.test.ts`, fake ports). ## Kretz Aura scale (direct weight over RS-232, 2026-09-25)

`features/sale/scale-weight.ts` (+ `scale-weight-parser.ts`, `ScaleWeightSettings.tsx` in the Mostrador gear panel) reads the weight straight from a Kretz Aura Eco over Web Serial, following the manufacturer's manual (Aura Eco Rev.01 §16, https://www.kretz.com.ar/shop/balanza-aura-eco-332/document/11): 9600 baud, 8 data bits, no parity, **2 stop bits**, straight (1:1) DB9 male–female cable (scale pin 2 Tx, 3 Rx, 5 GND), scale menu COMUNI → "A pedido de peso"; the app sends "W" and gets `2,XX.XXX,CR` (with price/amount variants). The parser is deliberately tolerant because the manual doesn't say whether the commas / leading "2" are literal; activation therefore requires a cashier-confirmed test read ("¿coincide con la pantalla de la balanza?"). Verified only against a simulated serial port and unit tests — NOT yet against a real Aura. If reading fails Mostrador adds nothing (never defaults to 1 kg). Separate from `features/inventory/scale-serial.ts` (PLU upload, Report LT protocol, 115200 baud); the Aura's "Datos" mode (iTegra/JDataGate) has an undocumented protocol, so PLU upload to the Aura is UNCONFIRMED: `scale-serial.ts` now has `stopBits` in its settings and `autoDetectScale()` (button "Detectar mi balanza automáticamente" in ScaleSyncPanel) which sweeps baud/stop bits/equipment letter/ID with the 0001 ping (Aura preset first: 9600, 2 stop bits, letter C, ID 01) hoping the Aura's Datos mode speaks the same Kretz frame protocol as the Report LT. Tested only against simulated ports; the first real Aura test decides.

**First real Aura (client, 2026-10-01).** The client used Stock → "Balanza por cable" with the Report LT defaults (115200 baud, 1 stop bit), so the scale never answered. Three bugs of ours were found and fixed:
1. `connectScalePort` ("Volver a elegir puerto") never opened the port picker when any port was already authorized; it silently took `getPorts()[0]`. It now always calls `requestPort()` and remembers the chosen port by USB vendor:product (`patagonia-scale-serial-port`).
2. `autoDetectScale` accepted ANY bytes as "found" (noise, or the scale in continuous weight mode). It now requires a Kretz-shaped response (`isKretzResponse`: starts with 0x07, contains EOT).
3. The drain loop in `exchangeWeightFrame` had no time limit, so endless noise would hang Mostrador. It is now capped at 400 ms.

New **"Probar todo"** (`diagnoseScaleLink`):
- At 9600 baud / 8N2 it listens passively and sends "W" (weight modes), then sweeps the Kretz 0001 ping (Datos mode).
- The verdict is one of:
  - `peso`: the cable works; switch the scale to Datos to send prices.
  - `datos`: the scale answered and the settings were saved.
  - `bytes`: data arrives but in a format we don't understand.
  - `nada`: physical problem (wrong port, cable not straight 2-2/3-3/5-5 with the male end at the scale, or adapter driver).
- The port is described by its USB chip (CH340, PL2303, FTDI or CP210x).
- Tests: `scale-diagnosis.test.ts`.

Manual pages 42–45 were re-read: the Datos mode is documented only for iTegra/JDataGate, so PLU upload to an Aura is still unconfirmed.

**Per-model drivers (2026-10-01, owner goal: send PLU/prices to the Aura without iTegra).** The source of truth is `docs/BALANZAS_KRETZ.md`: every fact tagged real / documentado / terceros / hipótesis / desconocido, with its source, plus the discovery plan, the Kretz e-mail draft and plan C (Bluetooth HCI snoop with iTegra Mobile, or a serial monitor with iTegra; never decompiling).

## Systel scales (module started 2026-10-04, NOT published)

`features/inventory/systel/` is independent of every Kretz file (nothing in `kretz/` or `scale-serial.ts` was touched). The source of truth is `docs/SYSTEL_INFORME.md`, built from Systel's official downloads (protocol Cuora 2 V4.0 and Cuora Max V6.0/V6.2/V7.0, the Qendra CSV import, the Cuora Neo CSV).

- **Frame:** address byte + function byte + ASCII data + XOR byte. The frame ends on silence.
- **Connection:** Cuora Max over USB = FTDI at 115200 baud.
- **Product layouts:** there are 4 (`cuora2`, `max60`, `max62`, `max7`). They differ by firmware, so the layout is detected from the read-reply length and Patagonia only writes the layout it read.
- **Function whitelist** (`assertSystelFunctionAllowed`):

(The token lives in the Windows user env var `NETLIFY_AUTH_TOKEN`; read it with PowerShell `[Environment]::GetEnvironmentVariable('NETLIFY_AUTH_TOKEN','User')` if the current shell lacks it. Run netlify-cli from `apps/web`, not the repo root — from the root it detects the npm-workspaces monorepo and hangs forever on an interactive "which project?" prompt it can't ask non-interactively.) Requires `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` set in Netlify env regardless of deploy method. The site belongs to the Netlify team `francisco-nesii`, so only a personal access token created in THAT account can deploy (the `carnespatagoniaf@gmail.com` login saved by `netlify login` can only read it). Before replacing a stored token, prove the new one can write (run `draft`).

**Repo layout gotcha:** the actual git repo root (`C:\Users\g\Documents\GitHub\patagonia-os\` on the owner's machine) is **one level above** this `patagonia-os-v312/` folder — `package.json`, `netlify.toml`, etc. all live inside `patagonia-os-v312/`, not at the repo root. Netlify's **Base directory** setting must be `patagonia-os-v312` or the build fails immediately (it did, the first time this was connected) because it can't find `package.json`. Keep this in mind for any other repo-root-relative tooling (CI, other deploy targets) — this is not a normal single-project repo root.
